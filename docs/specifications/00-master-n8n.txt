## HYBRID

Tiene una parte de lógica en Supabase y otra de orquestación externa en n8n.

Ejemplo:

Una cita es confirmada de forma autorizada en Supabase; n8n recibe el evento, prepara y envía la notificación permitida y devuelve el resultado del proveedor.

La decisión final y el estado empresarial permanecen en Supabase.

## MANUAL ASSISTED

Requiere intervención humana porque no existe conexión oficial o autorización suficiente.

Ejemplo:

Conciliación de citas con OKVET sin API autorizada.

## BLOCKED

Existe dependencia externa no resuelta.

Nunca declarar BLOCKED como IMPLEMENTED.

# 4. INFRAESTRUCTURA N8N

## 4.1 Selección de despliegue

Evaluar n8n Community Edition autohospedado.

Comprobar las condiciones de la Sustainable Use License para el uso interno previsto.

No asumir que el alojamiento es gratuito.

Si existe una instancia n8n conectada, inspeccionarla antes de desplegar otra.

## 4.2 Producción

Diseñar una instalación mediante Docker Compose apropiada para el entorno seleccionado.

Preferir:

n8n estable.

PostgreSQL dedicado para datos internos de n8n.

Persistencia.

HTTPS.

Reverse proxy.

Dominio propio o subdominio autorizado.

Credenciales cifradas.

Copias de seguridad.

Monitoreo.

Actualización controlada.

Separación de entornos.

## 4.3 Configuración

Documentar:

N8N_HOST.

N8N_PROTOCOL.

WEBHOOK_URL.

GENERIC_TIMEZONE.

TZ.

N8N_ENCRYPTION_KEY.

Conexión a PostgreSQL.

Variables de credenciales.

Políticas de ejecución.

Rotación de secretos.

Configurar America/Bogota como zona horaria operativa inicial.

No colocar tokens reales en GitHub.

No utilizar variables de desarrollo inseguras en producción.

## 4.4 Seguridad

Deshabilitar o restringir nodos peligrosos que permitan ejecución arbitraria innecesaria.

No instalar nodos comunitarios desconocidos sin revisión.

Configurar autenticación del administrador.

Limitar acceso a la instancia.

Restringir endpoints públicos.

No exponer PostgreSQL a Internet sin necesidad.

Implementar rate limiting donde corresponda.

Configurar monitoreo de fallos.

Ejecutar auditorías de seguridad de n8n.

Documentar procedimientos de restauración.

## 4.5 Principio de mínimo privilegio

n8n no debe tener acceso general de escritura a todas las tablas.

Las operaciones sensibles deben ejecutarse mediante endpoints de Supabase con autenticación de servicio, autorización por operación y validación de datos.

Nunca exponer la clave privilegiada de Supabase en el navegador.

Crear un sistema de eventos empresariales versionados.

Campos mínimos:

idempotency_key

source_system

retry_count

## Reglas

Cada evento tiene identificador único.

Los consumidores deben ser idempotentes.

Los eventos deben conservarse de forma durable.

Los reintentos no deben duplicar efectos.

Las acciones que requieran confirmación humana no pueden saltarse esa etapa.

Implementar un patrón transactional outbox apropiado para evitar inconsistencias entre cambios de negocio y publicación de eventos.

Utilizar Supabase Queues o una cola equivalente cuando corresponda.

No prometer entrega exactamente una vez a proveedores externos: diseñar procesamiento al menos una vez con deduplicación, reconciliación y comprobación de efectos.

## Importante

No tratar cualquier encabezado personalizado como prueba suficiente de autenticidad.
