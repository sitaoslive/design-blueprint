# 4. DECISIÓN ARQUITECTÓNICA DEL WEBHOOK

Antes de configurar un WhatsApp Trigger, verifica si ya existe un receptor registrado en Meta.

IMPORTANTE:

El nodo WhatsApp Trigger de n8n puede gestionar el registro de una URL de webhook al publicarse.

No permitas que una configuración nueva reemplace accidentalmente un callback utilizado por otra integración.

Evalúa dos opciones.

## OPCIÓN A — GATEWAY SEGURO DE SUPABASE

Preferida si necesitamos un punto de entrada centralizado, control de autenticidad, trazabilidad y procesamiento duradero.

Meta
→ Supabase Edge Function / Gateway
→ Verificación criptográfica
→ Registro persistente
→ Outbox
→ CORE-01
→ CORE-02.

## OPCIÓN B — WHATSAPP TRIGGER DE N8N

Utilizar únicamente si es compatible con la configuración real, mantiene validación de autenticidad adecuada y no interfiere con otros receptores.

Antes de utilizarla:

- Verificar cómo registra el webhook.
- Verificar manejo de firmas.
- Verificar eventos soportados.
- Verificar recuperación de entregas.
- Verificar si el proyecto necesita un gateway adicional.
- No publicar sin autorización.

Selecciona la arquitectura basándote en seguridad y compatibilidad, no en el menor número de nodos.

No usar ambos como receptores principales sin un diseño explícito.

# 5. SEGURIDAD DEL WEBHOOK DE META

Implementar los mecanismos oficiales de autenticación.

## Verificación inicial

Gestionar la solicitud de verificación del webhook según la especificación oficial:

- Verify token configurado.
- Verificación de valor recibido.
- Respuesta del challenge.
- Rechazo de solicitudes incorrectas.

## Eventos POST

Verificar:

X-Hub-Signature-256.

Calcular HMAC-SHA256 sobre los bytes originales del cuerpo recibido con el App Secret correspondiente.

Realizar comparación de forma segura y resistente a ataques temporales.

No verificar sobre JSON reserializado.

No confiar en datos del remitente sin validar la autenticidad de la notificación.

## Requisitos

- HTTPS.
- Firma válida.
- Tamaño máximo de payload.
- Validación de esquema.
- Limitación de abuso.
- Separación de entornos.
- Registro mínimo de errores.
- Rechazo de payloads alterados.
- Deduplicación.
- Protección contra replay mediante persistencia y controles aplicables.
- No exponer secretos.

Responder al proveedor únicamente después de alcanzar un punto durable del proceso, según el contrato elegido.

No demorar excesivamente el ACK ejecutando IA dentro de la petición webhook.

No responder OK si el evento no fue aceptado o persistido de forma confiable.

No debemos generar necesariamente cuatro respuestas desconectadas.

Evaluar un mecanismo de agrupación breve y configurable, siempre que no retrase respuestas críticas.

## Reglas

- Agrupar mensajes consecutivos cuando sea apropiado.
- Mantener orden.
- No perder eventos.
- No mezclar conversaciones.
- No mezclar clientes.
- Utilizar locks persistentes.
- Evitar dos agentes simultáneos.
- Detectar cambio de control humano.
- Revalidar el estado antes de preparar respuesta.
- No retrasar escalamiento de posibles urgencias.

El procesamiento debe ser tolerante a mensajes fuera de orden y a la llegada simultánea de eventos.
